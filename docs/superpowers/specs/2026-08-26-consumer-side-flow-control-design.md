# 消息推送中台消费侧流量治理设计

日期：2026-08-26  
状态：待用户审阅

## 1. 背景与目标

当前发送入口在消息入队前执行 Redis 固定窗口计数。普通消息命中限额后写入
`next_attempt_at = now() + 5s`，高优先级消息则直接绕过限额。这个设计存在四个问题：

1. 固定等待 5 秒与渠道真实可用容量无关，可能等待过长，也可能 5 秒后再次形成流量尖峰。
2. 流量治理发生在入口，混淆了“可靠受理”和“渠道发送速度”两个职责。
3. 高优先级绕过全部限额，可能打穿短信、邮件或飞书供应商的硬性 QPS 上限。
4. Kafka 中转路径不会执行 MySQL 的 `next_attempt_at` 逻辑，两种队列后端语义不一致。

本次改造目标：

- 请求通过校验并可靠入队后立即返回 `msgId`。
- 超出瞬时处理能力的消息保留在持久化队列中，由消费者平滑处理。
- 同时保护平台、渠道供应商和租户，避免单一业务占满系统。
- 高优先级获得更高资源份额，但不能突破渠道硬限额和平台安全水位。
- 限流不进入失败重试；只有真实推送失败才执行退避重试和死信处理。
- MySQL 与 Kafka 两种中转后端保持相同的业务语义。

非目标：

- 不承诺在入口 QPS 高于渠道容量时仍立即完成真实推送。
- 不在本次改造中引入新的外部中间件或配置中心。
- 不修改已有邮件、短信和飞书供应商 SDK 的具体调用方式。

## 2. 调研依据

### 2.1 阿里公开实践

阿里云 RocketMQ 官方文档明确指出，消费失败重试不应被用作限流。正确方式是延迟获取
消息，让超出消费能力的消息堆积在 Broker 中。AHAS 与 RocketMQ 的组合方案采用匀速
处理，将突发消息平摊到后续空闲时间。

资料：

- <https://help.aliyun.com/zh/apsaramq-for-rocketmq/cloud-message-queue-rocketmq-5-x-series/developer-reference/consumption-retries>
- <https://help.aliyun.com/zh/ahas/use-ahas-to-throttle-the-consumption-of-apsaramq-for-rocketmq-messages>

### 2.2 字节公开实践

字节技术团队公开的抖音支付高峰流量实践采用“入口受理后返回、队列承接洪峰、消费前
获取令牌”的生产者—消费者模型，并分别按照上游业务能力和下游资产能力做分层限流。

资料：

- <https://blog.csdn.net/ByteDanceTech/article/details/125419247>

该资料是特定高并发业务的公开实践，不代表字节内部完整消息推送中台架构。本设计只借鉴
其分层控速思想。

## 3. 方案比较

### 方案 A：入口超限直接返回 429

优点是实现简单、不会产生队列积压。缺点是业务消息需要调用方自行重试，可靠性和接入体验
较差。该方式仅保留为平台过载时的最后保护，不作为正常业务限流手段。

### 方案 B：按渠道做单层消费限速

所有消息先入队，消费者按照短信、邮件和飞书渠道 QPS 匀速发送。该方案能够修复固定延迟
问题，但无法阻止一个租户耗尽全部渠道资源，也不能提供严格的优先级保障。

### 方案 C：分层令牌桶与公平消费调度

所有消息可靠入队，在消费端同时检查平台、渠道和租户配额，并按优先级与租户进行加权公平
调度。该方案复杂度高于单层限速，但能统一解决平台保护、供应商配额、租户隔离和优先级
保障问题。

选定方案：方案 C。

## 4. 总体架构

新增以下核心组件：

### 4.1 `AdmissionGuard`

只负责入口平台过载保护，不处理业务渠道配额。

- 正常水位：所有合法消息可靠入队。
- 软水位：拒绝低优先级新消息并返回 HTTP 429。
- 硬水位：拒绝低、中优先级消息；高优先级仅在队列仍可可靠写入时受理。
- 队列或数据库不可用：返回 HTTP 503，不返回虚假成功。

水位依据包括队列积压数量、最老待处理消息年龄、线程池拒绝数和数据库连接池等待情况。
阈值通过配置项管理，初始值由改造后的容量测试确定，不在代码中写死。

### 4.2 `DispatchQuotaService`

使用 Redis Lua 实现分布式分层令牌桶。一次 Lua 调用同时检查并扣减以下配额，避免部分
扣减：

1. 平台总发送速率。
2. 渠道供应商硬限额，例如短信、邮件、飞书各自的 QPS。
3. `tenant + sourceId + channel` 业务配额。

每个桶保存当前令牌数和最近补充时间，支持：

- 稳定补充速率 `refillRate`。
- 短时突发容量 `burstCapacity`。
- 原子获取令牌。
- 返回下一枚令牌的预计可用时间。

高优先级可以借用普通业务的空闲份额，但不得绕过平台总量和渠道供应商硬限额。

Redis 不可用时消费侧采用 fail-closed：暂停真实渠道推送，让消息继续保留在持久化队列，
同时告警。这样不会因限流组件故障打穿供应商。

### 4.3 `FairDispatchScheduler`

采用两级加权公平调度：

1. 优先级权重默认为高:中:低 = 6:3:1。
2. 同一优先级内按租户轮询，避免单一租户独占资源。

未使用的份额允许其他优先级借用；低优先级保留最低服务份额，避免永久饿死。调度器只在
`DispatchQuotaService` 成功取得全部令牌后，才把任务提交给渠道推送线程池。

调度器本地等待区必须有界。达到上限后停止从 Kafka 拉取或停止从 MySQL 领取新消息，
利用持久化队列自身形成反压，不能无限堆积 JVM 内存。

### 4.4 `RecipientFrequencyPolicy`

用户防打扰属于业务策略，不等同于系统限流：

- 按 `tenant + recipient + channel + messageType` 统计发送频次。
- 低优先级消息超过频次后标记为 `SUPPRESSED`，不做无限期排队。
- 高优先级安全通知默认不受营销防打扰规则影响，但仍受渠道硬限额约束。
- 被抑制的消息保留审计原因，便于业务查询。

## 5. 数据流

### 5.1 接入与入队

1. 业务方调用 `POST /msg/send_msg`。
2. 完成认证、租户校验、模板校验和参数校验。
3. `AdmissionGuard` 检查平台水位。
4. 消息可靠写入 MySQL 队列表或 Kafka Topic。
5. 返回 `msgId`，表示“中台已可靠受理”，不表示供应商已经发送成功。

入口不再执行来源/渠道业务限流，也不再给新消息写固定的 5 秒延迟。

### 5.2 消费与推送

1. 队列适配器按有界预取量向 `FairDispatchScheduler` 提交消息。
2. 调度器解析模板，得到租户、来源、渠道和优先级。
3. 执行用户防打扰策略；命中后记录 `SUPPRESSED` 并结束。
4. 根据优先级和租户选择下一条候选消息。
5. `DispatchQuotaService` 原子获取平台、渠道和租户三层令牌。
6. 获取成功后调用邮件、短信或飞书策略服务。
7. 成功则记录 `SUCCESS`；真实发送失败则进入重试流程。

### 5.3 MySQL 队列适配

- 只领取本地调度器剩余容量以内的消息。
- 保留 `FOR UPDATE SKIP LOCKED` 原子抢占。
- 已领取但进程崩溃的消息继续由 stale-processing 恢复机制重新变为 `PENDING`。
- `next_attempt_at` 只用于真实失败后的退避重试，不再用于限流；定时消息继续走现有独立定时队列表。

### 5.4 Kafka 队列适配

- 保留高、中、低独立 Topic 与并发度。
- 本地调度器达到容量上限时暂停对应 Listener Container，容量恢复后继续拉取。
- 只有真实推送成功、被防打扰策略终结，或失败消息已可靠进入重试/死信后才提交 ACK。
- 限流等待不增加重试次数，不将消息重新发送到 retry Topic。

## 6. 失败处理

- 参数或模板错误：入口返回 400，不入队。
- 平台软过载：按优先级返回 429，并提供 `Retry-After`。
- 队列不可写：返回 503，调用方可使用相同 `msgID` 重试。
- Redis 配额服务不可用：暂停消费者并告警，消息保留在队列。
- 渠道临时失败：指数退避并加入抖动，达到上限后进入 DEAD。
- 渠道永久错误，例如号码格式错误：直接进入最终失败，不做无意义重试。
- 进程崩溃：Kafka 依靠未提交 offset 重投；MySQL 依靠 stale-processing 回收。

## 7. 配置与可观测性

新增可动态刷新的配置：

- 平台总 QPS 与突发容量。
- 各渠道供应商 QPS 与突发容量。
- 各租户/来源/渠道 QPS。
- 高、中、低优先级权重。
- 本地调度器容量与预取上限。
- 防打扰窗口与次数。
- 入口软、硬水位。

新增指标：

- 各队列积压数量和最老消息等待时间。
- 平台、渠道、租户实际发送 QPS。
- 各层令牌不足次数和等待时间。
- 各优先级、租户的调度数量与等待时间。
- HTTP 429/503 数量。
- `SUCCESS`、`SUPPRESSED`、重试和 DEAD 数量。
- 本地调度器深度及 Kafka pause/MySQL 停止领取时长。

## 8. 迁移策略

1. 增加新配置、指标与 `DispatchQuotaService`，保持旧逻辑可开关回退。
2. 引入 `FairDispatchScheduler` 和有界反压，先接入 MySQL 消费路径。
3. 接入 Kafka Listener 的暂停、恢复和 ACK 语义。
4. 将业务配额检查从 `SendMsgServiceImpl` 移到消费调度链路。
5. 删除固定 5 秒限流延迟以及高优先级绕过渠道硬限额的逻辑。
6. 保留 `next_attempt_at` 供真实失败退避使用。
7. 通过灰度配置逐步启用租户配额与防打扰策略。

## 9. 验证标准

- 入口突发 QPS 高于渠道容量时，接口能可靠受理且消费者按配置速率平滑发送。
- 不再出现每隔固定 5 秒形成的二次流量尖峰。
- 高优先级在积压时获得主要资源，但低优先级持续获得最低份额。
- 单一租户持续灌入消息时，其他租户仍能获得其配置份额。
- 高优先级不会突破短信、邮件或飞书供应商硬限额。
- 限流等待不会增加 retry count，也不会进入 retry Topic/表。
- Redis 暂时不可用时不丢消息、不打穿供应商，恢复后继续消费。
- Kafka 与 MySQL 两种中转模式通过相同的契约测试。
- 真实渠道失败仍按既有退避策略重试，超过上限进入 DEAD。
- 压测报告同时给出受理 QPS、真实发送 QPS、积压量和最老消息等待时间，避免只看入口吞吐。

## 10. 设计决策与 ADR 候选

建议后续记录以下 ADR：

1. 将业务限流从生产入口迁移到消费调度端。
2. 采用 Redis 分层令牌桶而非固定窗口计数。
3. 采用优先级加权与租户轮询组合的公平调度。
4. Redis 配额服务故障时消费侧 fail-closed。
5. 将防打扰建模为 `SUPPRESSED` 业务终态，而不是失败或延迟重试。

## 11. 已知假设

- Redis、MySQL 和 Kafka 仍沿用当前单机部署方式，本次不设计跨机房容灾。
- 渠道供应商配额可由运维或业务管理员提供并配置。
- 调用方能够区分“已受理”和“已送达”，并通过消息记录查询最终状态。
- 当前项目规模允许先使用 Redis Lua 实现全局配额，不引入独立限流服务。
